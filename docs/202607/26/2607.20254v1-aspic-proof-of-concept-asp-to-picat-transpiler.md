## 摘要
本文介绍ASPIC，一个新的概念验证库，它将扩展语法的ASP-Core-2程序转换为Picat谓词，这些谓词可以立即使用集成的Picat SAT求解器求解，或嵌入到更大的Picat程序中（"Picat中的ASP"），并且反过来可以利用各种Picat谓词和函数（"ASP中的Picat"）。初步测试表明，在缺乏正循环且不使用特殊Picat特性的程序上，与clingo具有良好的兼容性。通过嵌入式Picat，它还能有效利用ASP原子和有限域变量进行建模，触及clingcon的应用领域，并且进一步支持非线性约束的建模。

## Abstract
This article presents ASPIC, a new proof-of-concept library that converts extended syntax ASP-Core-2 programs to Picat predicates  that can be solved right away with the integrated Picat SAT solver, or embedded in larger Picat programs ("ASP in Picat"), and that can in turn make use of various Picat predicates and functions ("Picat in ASP"). The first tests prove good compatibility with clingo, on programs lacking positive loops and when the special Picat features are not used. With the embedded Picat, it touches the application field of clingcon as well, by being able to efficiently model with both ASP atoms and with finite domain variables, but goes beyond that by being able to model also non-linear constraints.

### 1. 论文的核心问题与整体含义（研究动机和背景）

- **背景**：Answer Set Programming (ASP) 是一种基于非单调逻辑的声明式范式，具有标准化的语法（ASP-Core-2）和清晰的稳定模型语义。现有的高效求解器如 clingo 在性能上已很出色（例如 N-Queens 问题可快速求解 5000 皇后），但在与外部数据处理、后处理步骤的集成方面，通常需要借助 Python 或 Lua 等过程式语言，缺少与逻辑编程语言的紧密融合。
- **核心问题**：ASP 程序在建模时缺乏对非线性约束（如乘法、指数等）的原生支持，且现有的扩展系统（如 clingcon、clingo-dl）仅支持线性或伪线性约束。此外，ASP 的接地（grounding）过程可能成为瓶颈（"grounding bottleneck"），而纯 ASP 求解器缺少灵活的预处理/后处理能力。
- **整体含义**：论文提出一个概念验证的转译器 ASPIC，将 ASP 程序自动转换为 Picat（一种多范式逻辑编程语言，支持约束编程、SAT 求解、表格化等）的谓词，从而实现 "ASP in Picat"（ASP 转 Picat 并用其内建求解器求解）与 "Picat in ASP"（在 ASP 中嵌入 Picat 代码以利用其丰富的约束和函数）。目标是弥合 ASP 与约束求解之间的鸿沟，提供超越线性约束的表达能力，并实现两种范式之间的双向集成。

### 2. 论文提出的方法论：核心思想、关键技术细节、算法流程

- **核心思想**：利用自然映射关系，将 ASP 对象直接转化为 Picat 约束编程（CP）构造。具体而言：
  - **ASP 原子**（接地后无边变量）→ 二进制 CP 变量（0/1），通过 Picat 的 map 数据结构存储，以原子的 ground 项作为键。
  - **ASP 规则**（head :- body） → 约束 `body → head`，即 body 为真时 head 必须为真。
  - **ASP 约束**（:- body） → 约束 `not(body)`。
- **Clark 完成（Clark Completion）**：为满足稳定模型的“支持性”（supportedness），对每条规则添加反向蕴含。对于 head 有多个规则的情况，添加 `head → (body1 ∨ body2 ∨ ...)`。注意：Clark 完成不能保证得到真正的稳定模型（例如正循环 `p :- p` 会产生虚假模型），因此仅适用于 **tight 程序**（无正循环）。
- **有限域（FD）变量**：通过线性组合二进制变量实现。例如，`fd(f, n)` 定义为 $\sum_{i=0}^{n-1} 2^i \cdot \text{aspic\_var}(f(i))$，其中 `aspic_var` 是用户定义的函数，将 ASP 原子映射到对应 CP 变量。
- **扩展语法**：使用 `&` 分隔符嵌入 Picat 代码段，这些代码执行后应返回 0/1 或 CP 约束值，可替代 ASP 原子。这使得在 ASP 中直接调用 Picat 全局约束（如 `tree`、`all_different`）和非线性约束（如乘法、平方）成为可能。
- **转换流程**：两遍扫描：
  1. 第一遍：收集所有事实和规则，提取所有可能的值域（universe U），确定迭代范围。
  2. 第二遍：生成 Picat 代码。使用 `foreach` 循环实现全称量化，例如 `foreach(X in U, Y in U) edge(X,Y) #=> path(X,Y) end`。启发式方法尝试缩小变量域，减少循环次数。
- **接地（Grounding）**：采用 on-the-fly grounding，避免一次性生成所有接地规则导致内存爆炸，但并不能解决搜索空间爆炸问题。

### 3. 实验设计：使用的数据集/场景、benchmark、对比方法

- **数据集/场景**：三个经典组合问题：
  - **N-Queens**（N皇后问题）：将 N 个皇后放在 N×N 棋盘上，互不攻击。使用 ASP-Core-2 的基数约束实现。
  - **Towers of Hanoi**（汉诺塔问题）：规划问题，将所有盘子从第一个柱子移动到第三个柱子，并满足大小约束。使用纯 ASP 编码。
  - **SEND+MORE=MONEY**（经典字母算术谜题）：为 8 个字母分配不同数字（0-9），且 S、M 非零，使加法成立。提供了纯 ASP 版本和利用 Picat FD 变量的混合版本。
- **Benchmark**：比较 ASPIC（转译后由 Picat SAT 求解器求解）与 clingo（版本 5.8.0，单线程及多线程）。对于 Towers of Hanoi，还测试了 clingo 的 64 线程模式。所有实验重复至少 10 次，取平均运行时间。
- **对比方法**：clingo（单线程，以及必要时多线程）。未与其他转译器（如 ASP2AR、ASP-PROLOG、ASP-FZN）进行性能对比，仅进行了定性比较。

### 4. 资源与算力

- **硬件**：两台 AMD EPYC 9654 96 核处理器，1.5 TB RAM。使用该强大设备以避免内存和线程限制对性能的影响。
- **软件**：Picat 3.9#4，clingo 5.8.0，操作系统 Ubuntu 24.04。
- **算力使用**：Picat 及 ASPIC 生成的代码均为单线程执行；clingo 支持多线程，但在 N-Queens 实验中多线程反而慢约 10%，因此 N-Queens 仅使用单线程；Towers of Hanoi 中比较了 clingo 单线程与 64 线程。作者未提及 GPU 的使用。

- **充分性评估**：

  - **消融实验**：无消融（如是否使用 Clark 完成、不同 grounding 策略的影响）。

### 6. 论文的主要结论与发现

- ASPIC 成功实现了从 ASP 到 Picat 的自动转译，并能利用 Picat 内建 SAT 求解器求解。
- 在 **tight 程序**（无正循环）上，ASPIC 的结果与 clingo 一致（兼容性良好）。
- 在某些问题上（如 Towers of Hanoi），ASPIC 的速度优于 clingo 单线程，甚至优于 clingo 64 线程（k=10 时，ASPIC 713s vs clingo 多线程 1329s）。
- 在 N-Queens 上，ASPIC 与 clingo 在较小规模（N≤512）时性能接近；但在较大规模（N=1024 时，ASPIC 944s vs clingo 183s）差距增大，主要归因于 ASPIC 的 grounding 方式不够高效。
- 通过嵌入 Picat 的 FD 变量和非线性约束，ASPIC 比 clingcon 能处理更丰富的约束类型（如乘法、全局约束 tree、all_different 等），例如 SEND+MORE=MONEY 的 FD 版本（108ms）远快于 clingo 纯 ASP 版本（756ms）。
- 目前 ASPIC 仅支持 Clark 完成，因此不能保证得到真正的稳定模型（仅适用于 tight 程序），这是主要限制。

### 7. 优点

- **方法简单直观**：映射关系清晰，生成的 Picat 代码可读性强，便于用户理解和进一步编辑。
- **双向集成**：同时实现 "ASP in Picat" 和 "Picat in ASP"，充分利用 Picat 丰富的约束库（全局约束、非线性约束、表格化等）。
- **扩展性**：超越了 clingcon 的线性限制，能处理多项式约束，拓宽了 ASP 的建模范围。
- **性能亮点**：在汉诺塔问题中表现出色，证明在某些具有结构化约束的问题上，利用 Picat 的 SAT 求解器可以获得竞争力。
- **开源可用**：代码发布在 GitHub 上（picat-lang/lib_ext），易于获取和复现。

### 8. 不足与局限

- **不支持非 tight 程序**：仅使用 Clark 完成，对于包含正循环的程序（如 p :- p）会产生非稳定模型。作者提出未来集成循环公式（如 ASSAT 方法），但目前尚未实现。
- **grounding 效率低**：采用显式、无过滤的 on-the-fly grounding，导致在变量域较大时（如 SEND+MORE=MONEY 纯 ASP）完全无法在合理时间内完成收敛。
- **聚合操作支持有限**：仅在约束中支持 `#min`、`#max`、`#count`、`#sum`，不能用于规则头部。
- **FD 变量语法实验性**：当前语法 `fd(f, n)` 和嵌入 Picat 的 `&` 语法较粗糙，例如需要将空格替换为下划线（`_`），且可能随用户反馈而改变。
- **缺乏全面系统对比**：只与 clingo 比较，未与 ASP2AR、ASP-PROLOG、ASP-FZN、clingcon、s(CASP) 等直接进行性能或表达力对比，结论的泛化性受限。
- **实验局限性**：无消融实验，对非 tight 程序未做测试，统计报告不完整（无标准差）。此外，未讨论内存使用情况（尤其是 grounding 阶段的内存峰值）。
- **可扩展性风险**：对于大型问题，ASPIC 的 grounding 和 CP 变量数量可能爆炸（例如 N-Queens 在 N=2048 时需要近千万 CP 变量），性能下降明显。
